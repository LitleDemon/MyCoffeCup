## Назначение и цели

**Назначение:** веб-приложение для кофейни, которое позволяет клиентам
просматривать каталог, собирать кастомные напитки (размер, добавки, температура),
оформлять заказы, а администратору — управлять товарами, топпингами, блогом,
заказами и просматривать статистику.

**Цели проекта:**
- Практическое применение Node.js + Express + MySQL на связанном наборе задач.
- Чистый JavaScript на клиенте без сборщиков — для прозрачной демонстрации.
- Полный цикл: от каталога и корзины до оформления заказа и админ-панели.
- Оригинальный дизайн-код «Eco Cardboard» (картонная палитра).

**Целевая аудитория:** посетители кофейни (гость и авторизованный пользователь),
администратор.

## Архитектура

```
┌─────────────────────────────────────────────────┐
│  Браузер                                        │
│  ┌──────────────┐  fetch  ┌──────────────────┐  │
│  │  HTML+CSS+JS │────────▶│  /api/*          │  │
│  │  localStorage│◀────────│  JSON            │  │
│  └──────────────┘         └────────┬─────────┘  │
└─────────────────────────────────────┼───────────┘
                                      │ HTTP
                          ┌───────────▼───────────┐
                          │  Express (server/)    │
                          │  ┌─────────────────┐  │
                          │  │  Middleware     │  │
                          │  │  (auth, upload) │  │
                          │  └────────┬────────┘  │
                          │           ▼           │
                          │  ┌─────────────────┐  │
                          │  │  Routes         │  │
                          │  └────────┬────────┘  │
                          │           ▼           │
                          │  ┌─────────────────┐  │
                          │  │  Controllers    │  │
                          │  │  (валидация)    │  │
                          │  └────────┬────────┘  │
                          │           ▼           │
                          │  ┌─────────────────┐  │
                          │  │  Models         │  │
                          │  │  (SQL)          │  │
                          │  └────────┬────────┘  │
                          └───────────┼───────────┘
                                      ▼
                          ┌───────────────────────┐
                          │  MySQL (coffee_shop)  │
                          └───────────────────────┘
```

**Принципы:**
- **Разделение слоёв.** Routes → Controllers (валидация + ответ) → Models (SQL). Контроллер не пишет SQL, модель не знает про `req/res`.
- **Единый формат ошибок.** Все ошибки → `{ "message": "..." }`, валидация → `{ "message": "...", "errors": [...] }`.
- **Никакой бизнес-логики на клиенте.** Цена, доступность топпингов и допустимость «холодного» варианта пересчитываются на сервере при создании заказа.
- **Корзина на клиенте.** В `localStorage` до оформления. Сервер получает уже готовый состав при `POST /api/orders`.

## Реализация по функциям

### 🔐 Аутентификация и роли

**Чем:** `bcryptjs` (хэш пароля), `jsonwebtoken` (токен), Express middleware.

**Как:**
1. **Регистрация** (`POST /api/auth/register`):
   - Валидация: `name ≥ 2`, `email` по regex, `password ≥ 6`.
   - Проверка на дубликат email → `409`.
   - `bcrypt.hash(password, 10)` → сохранение в `users.password_hash`.
   - Возврат `token` и публичных данных пользователя (без `password_hash`).
2. **Вход** (`POST /api/auth/login`):
   - Поиск пользователя по email, `bcrypt.compare` с хэшем.
   - Неверный email/пароль → одинаковое сообщение `"Неверный email или пароль"` (не раскрываем, что именно).
   - Возврат `token` + `user`.
3. **JWT:**
   - Payload: `{ sub: user.id, role }`.
   - Срок: 7 дней (`JWT_EXPIRES_IN`).
   - Подпись: `HS256` с `JWT_SECRET` из `.env`.
4. **Middleware:**
   - `requireAuth` — строгая проверка, `req.user` из БД, `401` при ошибке.
   - `optionalAuth` — мягкая проверка (для гостевого `POST /api/orders`).
   - `requireAdmin` — `403`, если `req.user.role !== 'admin'`.
5. **Клиент:** токен в `localStorage.token`, `api.js` добавляет `Authorization: Bearer <token>` ко всем запросам. При `401` — автоочистка.

### ☕ Каталог и фильтры

**Чем:** `GET /api/products`, `catalog.js`, `index.html`.

**Как:**
- Сервер возвращает товары с `ORDER BY is_seasonal DESC, id ASC` — сезонные сверху.
- Поддерживаются `?category=`, `?search=`, `?seasonal=1`.
- Клиент фильтрует ещё раз в памяти — для мгновенной реакции без повторных запросов.
- На карточке — выбор размера; цена пересчитывается в `sizePrice()`.
- Бейджи «Сезон» (`is_seasonal`) и «🧊 Холодный» (`has_iced_option`).

### 🥤 Страница товара

**Чем:** `product.html` + `catalog.js` (`initProductPage`).

**Как:**

### 🛒 Корзина

**Чем:** `cart.js`, `localStorage`.

**Как:**
- Позиция хранится как объект `{ key, product_id, name, price, image_url, product_sizes, size, toppings, iced, qty }`.
- Ключ `product_id_size_topings_iced` — гарантирует, что «Латте M горячий» и «Латте M холодный» — разные строки.
- Методы: `add`, `remove`, `updateQty`, `updateItem`, `clear`, `getTotal`.
- **Мердж при редактировании:** если новая конфигурация совпадает с уже существующей — `qty` суммируется, дубликат не появляется.
- Редактор позиции — модальное окно с размерами, температурой, топпингами, живым пересчётом цены.
- Синхронизация между вкладками через событие `storage`.

### 🎨 Открытка (стикеры и текст)

**Чем:** `stickers.js`, HTML5 drag&drop, Pointer Events.

**Как:**
- Канвас — `div` с `position: relative`.
- Стикеры — эмодзи из палитры (`draggable="true"` → `dataTransfer`).
- Текст — плашка с превью; перетаскивается как стикер.
- Каждый стикер: `{ id, type: 'emoji'|'text', content, x, y, scale, rotation }`.
- Координаты в процентах — не зависят от размера экрана.
- Управление маркерами прямо на стикере:
  - **Справа по центру** — ресайз (тянем от центра стикера, `--s` через CSS-переменную).
  - **Правый верхний угол** — поворот (угол `atan2` → дельта в градусах, `--r`).
  - **Левый верхний угол** — удалить.
- `transform: translate(-50%,-50%) rotate(var(--r)) scale(var(--s))` — масштаб и поворот без пересчёта координат.
- Сохраняется в `localStorage.stickers`; при заказе попадает в `orders.stickers` как JSON.

### 💳 Оформление заказа

**Чем:** `checkout.html` + `checkout.js` + `POST /api/orders`.

**Как:**
1. Клиент передаёт `items[{ product_id, qty, size_code, topping_ids, iced }]`, `stickers`, `payment_method`.
2. Сервер в **транзакции**:
   - Загружает товары и топпинги.
   - Проверяет: товар существует, размер доступен, топпинг активен и не истёк, `iced` допустим для этого товара.
   - Пересчитывает `price` каждой позиции: `base(size) + sum(toppings.price)`.
   - Считает `total`.
   - Вставляет `orders` (со снимком `stickers` и `payment_method`).
   - Вставляет `order_items` со **снимками** `name`, `price` и `options = { size, base, toppings, iced }`.
3. Возвращает полный заказ.
4. Клиент очищает корзину и открытку, редиректит на `/receipt.html?id=N`.

**Почему снимки:** если товар изменят или удалят — старый заказ остаётся с исторически верной информацией.

**Оплата:** `online` | `onsite`. Реальной интеграции с платёжной системой нет — поле сохраняется, статус `paid` ставит админ вручную.

## Ключевые технические решения

### 1. Снимки данных в `order_items`
`name`, `price`, `options` — копируются на момент заказа. Если товар изменится или удалится, чек останется исторически верным.

### 2. Транзакции при создании заказа
Все операции в `BEGIN / COMMIT / ROLLBACK`. Если хоть один товар или топпинг недоступен — заказ откатывается целиком.

### 3. JSON-поля для гибкости
`sizes`, `stickers`, `options` хранятся как `JSON`. Это избавляет от миграций при изменении структуры размеров или топпингов.

### 4. Валидация на двух уровнях
- **Клиент** — UX: подсветка ошибок до отправки.
- **Сервер** — безопасность: клиенту нельзя доверять (подмена `price`, `total`, `role`, `iced`).

### 5. Stateless JWT
Сервер не хранит сессии. Токен содержит `sub` и `role`. На каждый запрос `requireAuth` заново подгружает пользователя из БД — так роль в токене не «застревает», если её изменят.

### 6. localStorage для корзины
Серверу не нужна корзина — он получает готовый список при `POST /api/orders`. Быстро, работает без логина, но требует очистки при схемных изменениях.

### 7. Chart.js с фиксированной высотой
`.chart-wrap { height: 280px }` + `animation: false` + `resizeDelay: 200`. Убирает баг «бесконечного роста» canvas, который возникает при `maintainAspectRatio: false` без фиксированного родителя.

### 8. Локальный Chart.js
`/js/vendor/chart.umd.min.js`, не CDN. Работает без интернета при демонстрации.

## Безопасность

| Угроза | Мера |
|---|---|
| Открытый пароль в БД | `bcrypt.hash(password, 10)`, сравнение через `bcrypt.compare` |
| Подделка JWT | Подпись `HS256` секретом из `.env` |
| Подмена цены | `total` и `price` пересчитываются на сервере |
| Подмена автора статьи | `author_id = req.user.id` |
| Доступ к чужому заказу | Проверка `order.user_id === req.user.id` или `role === 'admin'` |
| SQL-инъекция | Параметризованные запросы (`pool.query(sql, params)`) |
| XSS в отрендеренных данных | `escapeHtml()` перед вставкой в `innerHTML` |
| Загрузка вредоносных файлов | `multer` фильтрует MIME + лимит 5 МБ + случайное имя файла |
| Недоступный товар/топпинг | Сервер проверяет перед вставкой, при ошибке — `400` |
| «Холодный» для десерта | Сервер проверяет `has_iced_option`, при ошибке — `400` |
